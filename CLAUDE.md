# Project State — LOOPIE

## MVP

**What it does:** A business manages owned communication (email/text/social messages), paid advertising campaigns, LOOPIE-hosted landing pages, first-party ad serving, and forms from one platform, with every lead and sale — regardless of which side generated it — landing in one shared CRM pipeline.

**Users:**

- Single role in V1: Business user (owner/manager/marketer). No MNC-staff-on-behalf-of-client portal, no agency/multi-account layer.

**In V1:**

- Contacts & Audiences — import/create contacts, channel eligibility/consent, segment into audiences (predefined + custom filters)
- Messages — compose/send email & text to an audience, save/reuse templates, automatic follow-up (max 2 steps, source-agnostic `LEAD_CREATED` trigger) that **actually runs** — see "Automation Execution" below
- Advertising — create a campaign (creative + platform + budget + dates), Deployment record per platform, tracked attribution redirect → landing page or lead capture on form submit
- **Landing Pages** — template-driven (not freeform) authoring: `LandingPageTemplate → LandingPage (draft) → PublishedPageVersion (immutable)`. LOOPIE-hosted at `/p/{slug}`, downloadable HTML export, draft/published lifecycle.
- **Forms** — first-class reusable `Form`/`FormField`, referenced by LandingPage. Submission is the canonical identity transition: anonymous session → `FormSubmission` → resolve/create Contact → create Lead, preserving Deployment/AdUnit/UTM attribution.
- **First-party advertising (AdUnit)** — a genuinely separate delivery mechanism from `Deployment` (external platforms). Served by `apps/ad-server`, a standalone deployable service sharing the same database. Feeds the same Lead/Sale spine via `sourceType = AD_UNIT`.
- Leads & Sales — one pipeline (NEW → CONTACTED → QUALIFIED → QUOTED → WON/LOST), Sale recording, attributed back to `sourceType`/`sourceMessageId`/`sourceDeploymentId`/`sourceAdUnitId` regardless of origin
- Results — Home (operational: what needs attention today) plus per-surface Performance (Campaigns → Performance, Messages → Performance); no standalone "Results"/"Reports" nav surface — see the 2026-08-27 IA revision below
- **Money & Ledger** — double-entry ledger for client ad funding, campaign budget authorization, platform spend, LOOPIE fees, credits/refunds, commissions, and payouts. Balances are derived from immutable entries.
- **Affiliate Attribution + Payouts** — a business's own referral partners: referral link/code → tracked session → Contact/Lead → Sale → Commission → Payout, backend-complete (no frontend pages yet) — see "Affiliate Attribution + Payouts" below.

**Parking lot (V2+):**

- Live Meta/Google/TikTok API connectors — V1 stores real `Deployment` records but platform status/spend/metrics are entered manually via `PATCH /deployments/{id}`, not synced live.
- Social post publishing to live platforms (V1 = compose/draft only).
- Branching/visual automation builder, >2-step sequences.
- Agency/multi-account/white-label management.
- Billing/subscriptions, deep role/permission systems.
- AI-generated content.
- Drag-and-drop landing-page builder (V1 is intentionally template-constrained — see below).
- Custom-domain DNS/cert provisioning for landing pages (the `customDomain` field exists; nothing automates it yet).
- A "Formerly" external landing-page template catalog/import flow (the data model — `LandingPageTemplate.businessId` nullable, `formatVersion` — is shaped for this, but no import mechanism exists).
- `DATE_REACHED` and `CONTACT_REPLIES` automation triggers — see "Automation Execution" below (**automation execution itself shipped 2026-08-27** — this used to be the whole parking-lot line; it's now just these two triggers).
- Affiliate frontend (portal/payee directory) — the backend chain shipped 2026-08-27 (Affiliate CRUD, referral tracking, auto-Commission on Sale); `pnpm pages:generate` will stub the new `/affiliates/*` routes when wanted.
- Live payment processor — `Payment` records client funding with idempotency/external refs, but no Stripe/processor plugin is installed; funding is recorded, not charged.

**Stack:** factory defaults (Vite + React, Fastify, Prisma + MySQL) — no overrides. Two Fastify services now: `apps/server` (contract-first, everything account/business-facing) and `apps/ad-server` (plain routes, public first-party ad serving only).

**Plugins:** file-upload (Asset library), transactional email + SMS send (Messages channel delivery) — not yet installed; to confirm against `references/plugin-catalog.md` before Phase 4/5. Ad-platform OAuth connectors deferred to V2. Railway deploy config now exists for both services (`Dockerfile` + `railway.json` each) — see the `railway` plugin and "Production Ops" below for `apps/server`'s, added 2026-08-27.

**Source docs:** `docs/00-unified-data-model.md` (canonical data model), `docs/00-unified-ia-navigation.md` (canonical IA/nav — **revised 2026-08-27**: `Home · Campaigns · Messages`, replacing the earlier `Home · Contacts · Messages · Advertising · Results`; "Campaigns" is the literal top-level label again, Contacts moved under Messages, Results/Reports dropped as a nav concept entirely in favor of per-surface Performance), plus the Messaging POC and Campaigns doc packs for UX/behavior detail per surface.

## Known Gap: Generated Stub Pages Have Naive Field Types — FIXED (2026-08-27)

`scripts/generate-pages.ts`'s Zod-schema inference (`buildZodExpr`) used to only ever produce `z.string()` — it didn't read the OpenAPI property's actual `type`/`enum`/array-ness. Every generated Create/Update page's form data was therefore all-strings, which didn't match the correctly-typed domain hooks (real enums, `number`, `string[]`, `Record<string, unknown>`). This was a pre-existing, systemic generator limitation (confirmed present for the original Contacts/Audiences pages too), not something the hook-writing session introduced — but it was the explicit blocker called out before starting Phase 4 UX work, so it was fixed at the generator level rather than patched per-page:

- `inferFieldType` now resolves `$ref` and reads the real OpenAPI shape: `boolean` → checkbox, `integer`/`number` → number input (`z.coerce.number()`), a string `enum` → `<select>` (`z.enum([...])`), `array` of strings/enums → a comma-separated "tags" input that preprocesses back into `string[]`/enum-array, and a free-form `object` (or array-of-object, e.g. `Form.fields`) → a JSON textarea that preprocesses into `Record<string, unknown>` (or `Record<string, unknown>[]`).
- `Form.tsx`'s `FieldConfig` gained `'number' | 'checkbox' | 'select' | 'tags' | 'json'` types (plus an `options` list for select/tags) and renders each with the right control; its `schema` prop type was loosened from `ZodSchema<T>` (input pinned to `T`) to `ZodType<T, ZodTypeDef, any>`, since `z.preprocess`-based fields (tags/json) legitimately have a different pre-transform input type than their output.
- A required array-of-nested-object field (only two exist site-wide: `CreateFormInput.fields`, `ImportContactsInput.contacts`) has no generic Zod reproduction of the target's exact shape — the generator casts the mutation call `as any` at the boundary for just those pages rather than pretending a generic JSON textarea can prove out a typed array of `FormFieldInput`/`CreateContactInput`. Both are also getting fully hand-built UI (Form builder, contact import) later, so the cast is a transient stopgap, not a real solution.
- Two path-param bugs were fixed alongside the typing gap: `create-form` pages nested under a parent resource (e.g. `POST /campaigns/{campaignId}/deployments`) now capture and merge the path param into the submitted body, same as `edit-form` already did; and a new `action` pattern was added for bare confirm-actions (`send`/`pause`/`resume`/`end`/`duplicate`/`publish` — path param, no request body), since their mutation hooks take the id directly (`mutationFn: async (campaignId: string) => ...`), not a wrapped object — the old generic `create-form` codegen passed `{}` and failed to typecheck for exactly these ~8 pages.
- **A separate, more severe bug was found while wiring navigation for the Landing Page vertical slice (below), not by typecheck:** `genAppTsx` registered a create-form and its sibling list (and an edit-form and its sibling detail) as two `<Route>`s at the _identical_ path (e.g. both `LandingPagesPage` and `CreateLandingPage` at `/landing-pages`). React Router silently renders only the first of two same-path siblings, so the second was permanently unreachable by URL — invisible to `tsc`, only visible by actually clicking through. Fixed generically: `create-form` routes now get a `/new` suffix, `edit-form` routes get `/edit` (e.g. `/landing-pages/new`, `/landing-pages/:landingPageId/edit`), applied across the whole app, not just landing pages. `genAppTsx`'s index/catch-all default was also changed from "first route in spec order" (previously hand-patched to `/home` once, per the deviation below) to "prefer a route literally named `/home` if one exists" — a generic rule so this doesn't need re-patching by hand every regeneration. All 76 pages and `App.tsx` were regenerated; typecheck stayed clean (still just the one `UpdateDeploymentPage` gap above).

All 76 stub pages were deleted and regenerated with the fixed generator (none had been hand-customized yet — Phase 4 hadn't started). `apps/web` now typechecks clean except for **one** pre-existing, separately-tracked gap: `UpdateDeploymentPage.tsx`, because no standalone `GET /deployments/{id}` operation exists in the API (see the `useDeployment` gap noted throughout this doc) — the generator can't invent an endpoint that isn't in the spec. Left open; not part of this fix's scope and not on the critical path of the Landing Page vertical slice that follows. **Closed 2026-08-27 — see "Deployment Contract Gap" below.**

Two earlier _generator_ bugs remain fixed from before, unrelated to this pass: `detectPattern` misclassified parameterless singleton GETs (`/home`, `/results`) as collection-list pages that called `.map()` on a plain object; `genDetailPage` handles the no-path-param case (no `useParams`, hook called with no args) instead of assuming every detail page has an id.

## Automation Execution (2026-08-27)

Automations were pure CRUD until now — stored, listed, pausable, but nothing ever ran them (`AutomationService.create()` had an explicit comment flagging this; `DashboardService.home()` had two literal placeholders, `followUpsDue` approximating as "count of active rules" and `automationErrors` hardcoded to `0`). Both are now real. Backend-only change by design — no new OpenAPI operations, no SDK/frontend surface; `AutomationLog` (already existed, already matched `docs/features/06-automation-rules.md`'s logging spec) stays the one user-visible execution history via the existing `GET /automations/{id}/logs`.

**Design: event-sourced scheduling, polling-based execution.** Not pure polling for everything — two of the four real triggers (status-change, sale-recorded) can't be reliably detected by scanning row state (`Lead.updatedAt` changes on _any_ edit, not just a stage change) but can be captured precisely at the exact call site that already exists and already writes the relevant `Interaction` row. Polling is used only for "is this due yet," which is naturally poll-shaped (wait N days, check a condition).

- **`apps/server/src/lib/automationScheduling.ts`** — `scheduleAutomationRuns()`, called from the four real trigger points: `identityResolution.ts`'s `insertOrReuseOpenLead` (`LEAD_CREATED`, only on genuine creation, not a reused open lead), `MessageService.send()` (`MESSAGE_SENT`, per recipient), `LeadService.update()` (`LEAD_STATUS_CHANGED`, right after the existing `STATUS_CHANGE` interaction write), `SaleService.create()` (`SALE_RECORDED`, right after the existing `SALE_RECORDED` interaction write). Creates a `PENDING` `AutomationRun` per matching active `Automation`; idempotent via `@@unique([automationId, triggerSourceId])` — a duplicate call (e.g. a retried request) is a safe no-op, verified in `automationExecution.test.ts`.
- **`AutomationRun`** (new model) — the scheduling record: `runAt` (`triggerEventAt` + `waitDays`), `status` (`PENDING`/`EXECUTED`/`SKIPPED`/`CANCELED`). Internal execution plumbing, not exposed via the API.
- **`apps/server/src/services/AutomationExecutorService.ts`** — `runDueAutomations()`, the pollable entrypoint. For each due `PENDING` run: checks **default stop conditions** (always, regardless of the automation's own `condition` — per the spec's separate "Default Stop Conditions" section: paused, contact opted out on the action's channel, a reply since the trigger, a sale since the trigger, the linked lead closed since the trigger), then the **rule-specific condition** if one is set (`CUSTOMER_STATUS` is interpreted as "contact has ≥1 Sale" — no deeper spec exists for that term, a documented judgment call), then fires the **action** (`SEND_EMAIL`/`SEND_TEXT` write an `Interaction` at the same fidelity as `MessageService.send()` — no live provider exists, this records the real event exactly like every other "send" in this app, not a regression; `CREATE_REMINDER` writes a `NOTE`-type `Interaction`, no new Reminder model; `CHANGE_LEAD_STATUS` updates `lead.stage`; `NOTIFY_USER` is the `AutomationLog` entry itself, no notification/inbox model exists; `STOP_SEQUENCE` cancels the contact's other `PENDING` runs). One bad run can't kill the tick — failures are caught, logged as `AutomationLog(outcome: FAILED)`, and counted, not thrown.
- **Poller wiring** (`apps/server/src/index.ts`) — a plain `setInterval` (default 60s, `AUTOMATION_POLL_INTERVAL_MS` to override), guarded off in `NODE_ENV=test`. No queue/worker infra exists anywhere in this repo, so this matches the existing single-process Railway deployment rather than introducing new infrastructure for it.

**Explicit scope boundary — 2 of 6 triggers are not wired**: `CONTACT_REPLIES` has no data source (`Interaction.type = REPLY` is only ever read, never written, anywhere in the codebase — no inbound webhook exists) and `DATE_REACHED` is under-specified (date relative to what? no spec guidance). Automations using either trigger remain valid, inspectable, and pausable — they just never produce a run. Not a bug; a stated boundary, same treatment as the `useDeployment` gap elsewhere in this doc.

## Affiliate Attribution + Payouts (2026-08-27)

**Affiliate → referral link/code → tracked session → Contact/Lead → Sale → Commission → Payout**, with two hard constraints honored throughout: affiliate attribution stays separate from acquisition `sourceType`, and all money owed/paid flows through the existing `FinanceService` — no new affiliate-balance concept anywhere. The financial half of this already existed before this pass: `Commission`/`Payout`/`PayoutItem` models, an `AFFILIATE_PAYABLE` ledger account kind, and `FinanceService.createCommission`/`markCommissionPayable`/`createPayout` were all built by the concurrent finance session (`docs/architecture/00-unified-data-model.md` states outright they were built "for future affiliate support") — **zero changes were made to any of it.** What this pass added is everything upstream of a Commission: an `Affiliate` model, referral-link tracking, and the one hook that produces a Commission automatically when a referred lead converts.

**Backend only, no frontend pages this pass** — same scope choice the finance session itself made for Money & Ledger.

- **Separation, not overloading**: a `Lead`'s `sourceType` (`MESSAGE`/`DEPLOYMENT`/`AD_UNIT`/`MANUAL`/`IMPORT`) keeps meaning exactly what it always meant — how the lead reached the business — completely unaffected by affiliate referral. `Lead.referringAffiliateId` (new, plain field, not part of the `sourceType`/`source*Id` group) answers the orthogonal question "who gets credit," stamped once at Lead creation only (same "first touch, not retroactive" rule already used for the `LEAD_CREATED` automation trigger). A pure affiliate referral (no ad `Deployment`/`AdUnit` involved) resolves with `sourceType: MANUAL` — the exact same fallback the acquisition chain already uses for any organic, non-ad-tracked submission — proven explicitly in `affiliateAttribution.test.ts`.
- **One non-invasive hook, not a parallel identity system**: both existing submission paths (`AttributionService.submitForm`, `LandingPageService.submit`) already resolve a verified session id and pass it to the one shared `resolveContactAndLead()` (`apps/server/src/lib/identityResolution.ts`) as `attribution.landingSessionId`, in every case including the no-ad-event fallback. The only new code lives inside that one function: after a genuinely new Lead is created, look up the most recent `AffiliateReferralClick` for that session id and stamp `referringAffiliateId` if found. Neither submission handler needed to change at all.
- **`GET /r/affiliate/{affiliateId}`** (`AttributionService.trackAffiliateClick`, public) — mirrors `GET /r/{deploymentId}` exactly, reusing its `clickRedirectUrl()`/`withSid()` helpers unmodified: mints/reuses a signed session id, writes an `AffiliateReferralClick` (a separate table from `AttributionEvent` — an affiliate isn't a paid ad platform, no reason to overload that model's campaign/deployment/ad-unit shape), redirects to the affiliate's destination landing page or fallback URL.
- **`SaleService.create()`** — one addition: if the sale's linked Lead has a `referringAffiliateId`, compute the commission amount (rule-type-dependent, see "Affiliate Policy" below since 2026-08-27) and call `financeService.createCommission(...)` with `payeeRef: "affiliate:${affiliate.id}"`, `sourceRef: sale.id`, and a deterministic `idempotencyKey` (`commission:sale:${sale.id}` — a retried request can't double-commission). Same post-commit, best-effort convention already used there for `SALE_RECORDED` automation scheduling. `Commission.payeeRef`/`sourceRef` are plain free-form strings, not relations — precisely so this works without the finance schema ever needing to know what an "affiliate" is.
- **No platform-wide default commission rate** — a business must consciously set one per affiliate; documented judgment call, no spec existed for this. (Originally percentage-only/always-required; see "Affiliate Policy" below for the rule-type split.)
- **`AffiliateService`** — CRUD (list/create/get/update/pause/resume), mirrors `AutomationService`'s exact shape. `referralCode` is globally unique (like `LandingPage.slug` — same reasoning: a clean public link, no business-id prefix), auto-generated with a retry-on-collision loop when omitted, explicit codes get a direct 409 like `LandingPageService.create`'s slug handling.
- **`Lead`'s response schema gained `referringAffiliateId`** (nullable, read-only) — the only change to an existing public API shape; no other endpoint, DTO, or finance route was touched.

## Affiliate Policy (2026-08-27)

The plumbing above worked but ran on unstated assumptions — percentage-only commission, no time bound between a referral and a still-payable sale, no way to undo a commission if a sale fell through, payouts requiring a human to pick commission ids by hand every time. Explicit policy, defined before any affiliate-facing UI gets built on top of guesses:

- **Commission rule type** — `Affiliate.commissionRuleType` (`PERCENTAGE` default | `FIXED`). `commissionRateBps` is now nullable; `commissionFixedAmountMinor` is new. Exactly one is set per rule type, validated in `AffiliateService` (app-level XOR, same reasoning as `AttributionEvent.deploymentId`/`adUnitId` — no DB constraint expresses it cleanly). `FIXED` commission is capped at the sale amount — a flat-rate affiliate can never earn more than the sale was worth.
- **Eligibility window** — `Affiliate.eligibilityWindowDays` (nullable = unlimited), checked in `SaleService.create()`'s commission hook, measured from the _actual referral click_ (`AffiliateReferralClick.clickedAt`, looked up via the lead's `landingSessionId`) — not from Lead creation, which is what a naive implementation would have used and would have made "eligibility window" mean something different from the standard cookie-window concept it's named after. Previously: no bound at all — a lead sitting open for months would still generate commission on eventual conversion. A skip writes an `Interaction` (`type: NOTE`) explaining why, so it's visible on the contact's timeline instead of silently absent.
- **Reversal** — **no "a sale was refunded" concept existed anywhere before this pass** (confirmed: no update/delete/reverse operation on `Sale` at all). New `POST /sales/{saleId}/reverse` (`SaleService.reverse`, idempotent): sets `Sale.reversedAt` (nullable timestamp, not a status enum — matches `Lead.closedAt`/`Automation.pausedAt`), reopens `Lead.stage` to `QUALIFIED` only if this was the lead's only active (non-reversed) sale, and reverses the linked `Commission` via a **new, additive** `FinanceService.reverseCommission()` (`apps/server/src/services/finance/payoutOps.ts`, mirrors `cancelCommission`'s exact style) — the one new code written inside the finance module across both affiliate passes, added specifically because "all money owed/paid flows through FinanceService" means a `Commission.status` mutation can't happen from anywhere else either. `PENDING` commissions are cancelled outright; `PAYABLE`/`PAID` ones (already ledger-posted) get reversed through the _already-existing_ generic `reverseTransaction()` in the same module, then marked `REVERSED` — a step `reverseTransaction` itself deliberately doesn't take, since it's a generic ledger primitive with no concept of "commission."
- **Payout threshold + cadence** — `Affiliate.payoutThresholdMinor` (nullable = no minimum), `payoutCadence` (`MANUAL` default | `WEEKLY` | `MONTHLY`), `lastPayoutAt`. New `apps/server/src/services/AffiliatePayoutService.ts`, `runDuePayouts()` — same pollable-entrypoint shape as `AutomationExecutorService.runDueAutomations()`, wired as a second `setInterval` in `index.ts` (`AFFILIATE_PAYOUT_POLL_INTERVAL_MS`, default 1h — cadence-based, not real-time). Sums `PAYABLE` commissions per affiliate; below threshold, left due for next tick rather than reset. `MANUAL` (the default) is never touched by the poller — `POST /finance/payouts` keeps working exactly as it always has for anyone who wants to pay by hand regardless of cadence.
- **Attribution model — first-touch, decided and documented, not made configurable.** Already true in the shipped code (`resolveContactAndLead` only stamps on genuine creation, never on a reused open lead) — this pass makes it an explicit, justified call rather than an implicit side effect of how the code happened to be written. Deliberately not building a first/last-touch toggle: nothing calls for per-affiliate variability here, and last-touch would need materially more machinery (re-evaluating attribution on every click within a lead's whole open window, not just once at creation) that isn't earning its cost speculatively.
- **`affiliatePolicy.test.ts`** (4 tests: fixed-rate math incl. capping, eligibility-window skip with the audit note, full reversal lifecycle incl. idempotency, threshold-gated cadence payout not firing early then firing once met with `MANUAL` affiliates provably untouched) plus **`affiliateDeals.test.ts`** (manager split identity + freeze after deal/manager change).

**Assignment layer (merged 2026-08-26):** `AffiliateClass` → `AffiliateDeal` (the policy source: rule type, rate XOR fixed amount, managerShareBps, eligibility window, payout cadence/threshold) → per-affiliate assignment (`classId`/`dealId`/`managerId`) and admin rate overrides. Sale resolves live policy once, writes immutable `SaleAffiliateSplit`, then `FinanceService` posts commissions from those frozen amounts. Changing a deal or manager later does not rewrite history. Manager share is a split of gross, not extra cost. First-touch and click-based eligibility are unchanged.

## Transactional Integrity Pass (2026-08-27)

Picked from a list of five candidate hardening assignments (campaign inventory reconciliation, landing-page capture immutability, transactional integrity, the deployment contract gap, production ops) as the highest-value next step given how many money- and pipeline-affecting writes had accumulated across sessions without a dedicated audit pass. Scope: make `MessageService.send()` atomic, fix a real Sale↔Lead consistency gap, and audit other multi-write service paths for missing `$transaction`.

- **`MessageService.send()`** — previously three sequential statements (`interaction.createMany`, `contact.updateMany`, `message.update`). A crash between them left the message stuck at `DRAFT`/`SCHEDULED` with interactions/contacts already written — a retry (or the caller's own retry logic) would re-send to every recipient, since the top-of-function "already sent" guard only protects a _completed_ send. Now one `db.$transaction`: either all three land or none do, so a retry after a genuine failure always starts clean.
- **Sale ↔ Lead contact consistency** — `SaleService.create()` accepted an independent `contactId` and `leadId` (both are plain fields on `CreateSaleInput`, not derived from each other) and never checked that the lead actually belonged to that contact. A sale could be recorded against Contact A while carrying Contact B's lead — corrupting the leadId's own `SALE_RECORDED` interaction/automation trail and this sale's attribution history. Now a straight `400` if `lead.contactId !== data.contactId`, checked inside the existing transaction before any write.
- **Other multi-write paths audited and fixed** (same "a crash partway through must not leave disagreeing rows" standard as the two above):
  - `LeadService.update()` — the stage `lead.update` and its `STATUS_CHANGE` interaction (the row `scheduleAutomationRuns`' idempotency key is derived from) are now one transaction; previously a lost interaction meant a stage change with no audit trail and a silently-dropped `LEAD_STATUS_CHANGED` trigger.
  - `CampaignService.update()` (creative-list diff: `deleteMany` + `createMany` + the campaign row) and `.pause()`/`.resume()`/`.end()` (Deployment/AdUnit status cascade + the campaign's own status write) — previously a campaign could end up "paused" while its deployments stayed `ACTIVE`, or a creative-list update could delete the old links and then fail to write the new ones.
  - `AudienceService.create()` (audience + its initial `AudienceMember` rows) and `.delete()` (member cleanup + the audience row itself).
  - `AutomationExecutorService`'s `SEND_EMAIL`/`SEND_TEXT` action (`Interaction` write + `contact.lastContactedAt` update) — previously could record the "sent" interaction but fail to update `lastContactedAt`, while the outer catch in `runDueAutomations` marked the run `CANCELED` (looking like nothing happened despite the interaction existing).
  - Checked and left alone: `identityResolution.ts`'s `resolveContactAndLead` (both callers already wrap it in their own `$transaction`), `SaleService.reverse()`'s sale/lead writes (already transactional; per-commission `reverseCommission` calls stay outside, matching the existing best-effort/idempotent-key convention used for automation scheduling and commission creation elsewhere), `CampaignService.create()`/`.duplicate()` (already transactional), and `ContactService.importMany()` (intentionally per-row, not atomic across rows — a partial import is the desired behavior, not a bug).
- **`transactionalIntegrity.test.ts`** (3 tests, hand-written, not generated): the two Sale↔Lead cases (mismatched contact rejected with no row written; matching contact accepted), plus a `MessageService.send()` rollback proof that forces a failure on the transaction's final statement via a Prisma `$use` middleware (fires for queries run inside an interactive transaction too, unlike mocking the model delegate directly, which does not intercept the separate `tx` client Prisma hands to the callback) and asserts zero interactions/contact updates survive, followed by a clean retry. Passes against `loopie_test` alongside the other five hand-written suites (28 tests total).

## Campaign Inventory Reconciliation (2026-08-27)

Picked as the next item off the same five-candidate hardening list the Transactional Integrity Pass came from (see that section) — flagged as the most important remaining _live-behavior_ gap, since it directly determines whether stale inventory keeps serving. Before this pass, `CampaignService.update()` could change `creativeIds` (swapping `CampaignCreative` join rows) but had no way to touch the actual `Deployment`/`AdUnit` rows those creatives had already spawned, and `platforms` couldn't be changed via the API at all after creation.

- **`lib/campaignInventory.ts`'s `createCampaignInventory()` → `reconcileCampaignInventory()`.** The old function only ever created rows (fine for `create()`/`duplicate()`, which start from nothing) and had no concept of "what already exists." The new function always diffs the full desired `platforms x creativeIds` set against a fresh read of the campaign's actual `Deployment`/`AdUnit` rows (any status) before deciding what to do — so it's the same function for a brand-new campaign (nothing exists → everything gets created, identical output to the old function) and an edited one (the real diff). `CampaignService.create()` and `.duplicate()` were switched to call it too, purely as a rename — their behavior is unchanged since there's never pre-existing inventory at those call sites.
- **The diff, per platform x creative combo:**
  - Still desired, already has a non-`ENDED` row → left completely alone (does not touch spend/impressions/status — a running Deployment mid-flight is never disturbed).
  - No longer desired, has a non-`ENDED` row → that row's status is set to `ENDED`. **Never a delete** — `Deployment`/`AdUnit` are referenced by `Lead.sourceDeploymentId`/`sourceAdUnitId`, `Sale`, `Interaction`, and `AttributionEvent`; deleting the row would either violate those FKs or silently sever attribution history. `apps/ad-server`'s `AdServeService` already only serves `status: 'ACTIVE'` ad units (pre-existing check, confirmed unchanged), so an `ENDED` row stops serving immediately.
  - Newly desired, no existing row at all → a new row is created at the same default status `create()` always used (`Deployment: PENDING`, `AdUnit: DRAFT`) — the business still manually flips it live, exactly like every other Deployment/AdUnit lifecycle transition in V1 (no live platform sync — see the Parking lot).
  - Newly desired, but a matching row already exists and is `ENDED` (a previously-retired combo coming back) → that row is **revived** (status reset to `PENDING`/`DRAFT`) instead of creating a second row for the same combo. Keeps one row per (campaign, creative, platform) tuple going forward rather than accumulating duplicates across repeated edits, while still not resurrecting it as falsely "already live."
- **`UpdateCampaignInput` gained `platforms`** (`packages/api-spec/openapi.yaml`, same enum + `minItems: 1` as `CreateCampaignInput` — a campaign can't be edited down to zero platforms; `POST /campaigns/{id}/end` is the existing "stop everything" primitive for that). This was a real, load-bearing gap: platforms were otherwise permanently fixed at creation, which made the entire "platforms change" half of this task unreachable through the API. SDK regenerated (`pnpm sdk:generate`); `useCampaigns.ts`'s hand-written `UpdateCampaignInput` type (kept separate from the generated types for the reason documented in the `CreateCampaignInput.platforms` deviation below) updated to match.
- **`CampaignService.update()`** now computes the _effective_ post-update `creativeIds`/`platforms` (falling back to the campaign's current values for whichever field wasn't sent in this particular `PATCH`) and always reconciles against that effective pair whenever either field is present in the request — so a platforms-only edit still reconciles correctly against the unchanged creative list, and vice versa, rather than only reconciling the one field that happened to be sent.
- **`campaignInventoryReconciliation.test.ts`** (3 tests, hand-written): dropping a creative and a platform from a running campaign retires exactly the combos that fell out (and nothing else) with zero deletions; removing then re-adding a combo revives the original row rather than duplicating it; a platforms-only update correctly reconciles AdUnits against the campaign's unchanged creative list. Passes against `loopie_test` alongside the other six hand-written suites.
- **Out of scope, left for later**: frontend surface for editing `platforms` post-creation (the generated `UpdateCampaignPage.tsx` stub would need regenerating to pick up the new field; no hand-built campaign-edit UI currently exposes it — `CampaignCreativesPage.tsx` only manages the creative-attach flow, not platform selection). Not touched here since the ask was specifically the backend reconciliation behavior.

## Landing-Page Capture Immutability (2026-08-27)

Next off the same confirmed priority list (after Campaign Inventory Reconciliation) — the previously-documented deviation "Form structure is not frozen into PublishedPageVersion" was a real capture-integrity gap, not just a documented quirk: a business could publish a page, then edit the attached Form's fields (add a new required field, drop a field, change what counts as an email/phone field), and every already-published, "immutable" page using that form would silently start rendering and validating against the new shape.

- **`PublishedPageVersion.formSnapshot`** (new nullable `Json` column) — freezes `{id, submitLabel, successMessage, fields: [...]}` for the form attached at the moment of publish, via a new `lib/formSnapshot.ts#snapshotForm()`. `LandingPageService.publish()` calls it inside the same transaction that writes `content`/`theme`, so all three are frozen atomically. `null` for pages with no form, and for any version published before this column existed (see the fallback below).
- **Consumers switched from live lookups to the frozen snapshot**: `LandingPageService.serve()` (the hosted `/p/{slug}` render) and `.submit()` (validation, required-field checks, and which field is the email/phone field used for identity resolution) now read `page.publishedVersion.formSnapshot` instead of querying the live `Form`/`FormField` rows. `loadFormForRender()`/`snapshotForm()` against the live tables are kept as an explicit **fallback only** for a `PublishedPageVersion` row that predates this column (`formSnapshot: null`) — those legacy versions intentionally keep the old live-lookup behavior since no earlier snapshot exists to fall back to. `LandingPageService.export()` (the draft-preview/download endpoint) was deliberately left untouched — it renders the current _draft_ working copy against the current live form by design, unrelated to what's hosted for existing visitors.
- **A second, previously-undetected bug fixed by the same change**: `submit()` was validating against `page.form` — the live, mutable pointer on the _draft_ `LandingPage` row — not `page.publishedVersion.formId`, the pointer actually pinned at publish time. `LandingPage.formId` can already be reassigned to a different Form via `PATCH /landing-pages/{id}` without republishing (same as `content`/`theme` staying draft-only until publish); before this fix, doing so would make `submit()` silently validate against the new, unpublished form's fields while `serve()` kept correctly rendering the old, published one — two different forms in play for what should be one immutable, coherent published experience. Fixed by having `submit()` resolve everything (both the frozen field shape and, per the point below, the liveness gate) off `page.publishedVersion.formId`, never `page.formId`.
- **Freezing structure is not the same as freezing existence — `isFormLive()`.** A pre-existing, already-shipped test (`publicAuth.test.ts`, from a concurrent session's public-capture hardening pass) established that soft-deleting a Form must immediately stop it from being served or submitted to on _any_ page using it, published or not — a deliberate spam/abuse control, not a bug. The first version of this fix broke that test by trusting `formSnapshot` unconditionally once present. Fixed with `lib/formSnapshot.ts#isFormLive()`: both `serve()` and `submit()` now check the _live_ Form's `deletedAt` (via the pinned `publishedVersion.formId`) as a separate gate before consulting the frozen snapshot — deleting a Form still takes effect everywhere immediately; only the field _structure_ of a still-live Form is what stays pinned to publish time.
- **`FormService.update()`'s wholesale field-replacement behavior is unchanged** (still deletes and recreates all `FormField` rows on any `fields` update) — that was never the problem; the problem was downstream consumers reading live state instead of a frozen copy. Its comment, the `updateForm` OpenAPI response description, and the stale "Form structure is not frozen" deviation bullet below were all updated to describe the new, correct behavior.
- **`landingPageCaptureImmutability.test.ts`** (2 tests, hand-written): publish → edit the live Form (drop a requirement, add a new required field, swap a field out) → the hosted page still renders and validates against the original frozen fields, a submission satisfying only the original requirements succeeds, one violating them still fails 400 → republishing freezes a fresh snapshot that does reflect the edit; plus a second test simulating a pre-migration row (`formSnapshot` forced to `NULL` via raw SQL) to prove the live-lookup fallback path. Passes against `loopie_test` alongside the other seven hand-written suites (33 tests total).
- **Found and fixed along the way, unrelated to this feature**: `packages/api-spec/openapi.yaml` had an unquoted YAML flow-mapping value (`description: Live /p/{slug} URL of...`) on the `AffiliatePortal`-style DTO added by a concurrent session — the literal `{slug}` inside an unquoted `{ ... }` flow mapping is invalid YAML and broke `SwaggerParser.dereference()` for the _entire_ spec, failing every test in the suite (not just landing-page ones) with a generic "must contain a valid specification" error. Fixed by quoting that one description string; did not touch the surrounding concurrent work otherwise.

## Production Ops (2026-08-27)

Last of the five original hardening candidates, picked by explicit user priority order after campaign inventory reconciliation, landing-page capture immutability, and the deployment contract gap. Three sub-items: shared-storage rate limiting, `apps/server`'s own Railway/Docker config, and permanent `loopie_test` isolation.

- **Rate-limit store — asked, decided against Redis.** Both `apps/server` and `apps/ad-server`'s public-write rate limiters used a plain in-process `Map<string, {count, resetAt}>` — correct only for a single process; with more than one Railway instance (or after a restart) each instance has its own counters, so the limit is trivially bypassed by load-balancing across instances. Put the choice to the user directly (Redis vs. a new DB table vs. a split) since it's a real infra/cost decision — no Railway project exists yet for this app to attach a managed Redis to, and `apps/ad-server`'s own schema comments already describe impression counting as deliberately "cheap, no per-row write," which a Redis-backed limiter would preserve but a DB-backed one works against on that specific high-volume path. Decided: **MySQL-backed, no new infrastructure** — consistent with this repo's established pattern of not introducing new infra when the existing shared database can do the job (same reasoning as Automation Execution's plain-`setInterval` poller, no queue system).
- **`RateLimitBucket`** (new model, `packages/db/prisma/schema.prisma`) + **`consumeRateLimit()`/`cleanupExpiredRateLimitBuckets()`** (new `packages/db/src/rateLimit.ts`, re-exported from the package's `client.ts` so both services import the identical implementation via `@project/db`, the same pattern already used for `issueSid`/`hashSessionToken`). A **fixed window keyed by its own boundary** (`` `${bucketKey}:${windowStart}` ``, `windowStart = floor(now / windowMs) * windowMs`) rather than a mutable `resetAt` column checked-then-reset — this means a single `upsert` is race-free with no read-then-write window between concurrent requests for the same key (MySQL's `INSERT ... ON DUPLICATE KEY UPDATE` under the hood is atomic per row), and no raw SQL or transaction was needed. `expiresAt` is set one window past the bucket's own so the periodic cleanup sweep can't delete a bucket while a request in its tail end is still about to increment it.
- **Both plugins switched from the in-memory `Map` to `consumeRateLimit`**, keeping their existing route-pattern allowlists and per-service `WINDOW_MS`/`MAX` values unchanged — only the storage backend changed, not the policy. Bucket keys are namespaced per service (`server:...` / `ad-server:...`) even though the two services' route paths don't actually collide, purely so the shared `RateLimitBucket` table's contents stay unambiguous to read.
- **Cleanup pollers** wired into both `index.ts` files (`RATE_LIMIT_CLEANUP_INTERVAL_MS`, default 10 min) — same plain-`setInterval`-guarded-off-in-test pattern as `AutomationExecutorService`/`AffiliatePayoutService`'s pollers; this is `apps/ad-server`'s first poller. Safe to run from either or both processes since they share one table.
- **A real, previously-unexercised production bug found and fixed, not by inspection**: both `apps/server/package.json` and `apps/ad-server/package.json` had `"build": "tsc"` / `"start": "node dist/index.js"`. Actually running `node dist/index.js` crashes immediately (`SyntaxError: Unexpected identifier 'global'` inside `@project/db`'s compiled output) — `@project/db`'s `package.json#main` points straight at its `.ts` source with no build step of its own, so plain `node` can't load it once `apps/server`/`apps/ad-server` themselves are compiled to CommonJS and try to `require('@project/db')`. This had never been caught because neither service's actual deployment path uses `pnpm start` at all — `apps/ad-server`'s existing Dockerfile already runs `tsx apps/ad-server/src/index.ts` directly in its `CMD`, bypassing the broken script entirely; the broken script itself was simply never exercised or fixed. Both `start` scripts now use `tsx src/index.ts` (verified live: `pnpm --filter server start` against `loopie_test` now actually serves `/health` correctly; previously it would have crashed on its first `@project/db` import).
- **`apps/server/Dockerfile` + `apps/server/railway.json`** (new) — mirror `apps/ad-server`'s existing files exactly (multi-stage build: install → `prisma generate` → typecheck → copy-only-what's-needed runtime image → `tsx` `CMD`), with the one real difference being `apps/server` also needs `packages/api-spec` copied into the runtime image (its `index.ts` reads `openapi.yaml` directly at startup for `fastify-openapi-glue` routing and the `/docs` UI), which `apps/ad-server` deliberately excludes since it isn't contract-first. Not verified with a real `docker build` — no Docker daemon available in this environment (WSL integration not enabled) — but the runtime `CMD` itself (`tsx apps/server/src/index.ts`) was verified to actually work via the `pnpm start` check above, and the copied-file list was checked against every `@project/`/relative-path import in `apps/server/src`.
- **`assertTestDatabaseUrl()`** (new, `packages/db/src/testGuard.ts`) — a structural safety net, not just a config default: `apps/server/vitest.config.ts` and `apps/ad-server/vitest.config.ts` already default `DATABASE_URL` to `loopie_test`, but a default is only a convention — an env file mistake, a future config refactor, or a CI environment that doesn't source `TEST_DATABASE_URL` could all silently point either suite's global-table-wiping `afterEach` at the real `loopie` database. Now both suites throw immediately and loudly (`apps/server/src/__tests__/helpers/setup.ts`, new `apps/ad-server/src/__tests__/helpers/testSafety.ts` wired as a `setupFiles` entry) if `DATABASE_URL` doesn't look like a test database, rather than silently proceeding to delete real data.
- **`rateLimit.test.ts`** (hand-written, both services): `apps/server`'s (6 tests) covers `consumeRateLimit`'s per-key limiting, independence between keys, two independent calls sharing one counter (the literal scenario this whole fix targets — simulating two separate server instances), fixed-window reset via `vi.useFakeTimers()`, `cleanupExpiredRateLimitBuckets` leaving live buckets alone, and the actual Fastify hook returning 429 end-to-end (a small standalone Fastify instance, since `buildTestApp()` never registers this hook — it's a bespoke harness for the OpenAPI-routed handlers, not `index.ts`'s real middleware stack). `apps/ad-server`'s (1 test) proves the same hook wiring for its own routes/limits, since the underlying `consumeRateLimit` is already exhaustively covered by the server-side suite. Both pass against `loopie_test` alongside every other hand-written suite; confirmed zero regressions by diffing the full stub-test failure list before/after (identical to the pre-existing baseline).

## Shared Database Policy (2026-08-27)

**The shared dev database (`loopie`) is no longer disposable test state.** It used to be safe to wipe (`setup.ts`'s global `afterEach` deletes every business/contact/lead/... row) because this repo held only this session's own work. That's no longer true: this same working tree also holds concurrent, independently-owned work — a full finance/ledger subsystem and public/auth hardening — landed by a parallel session on the same project. ## Deviations from Defaults

- **OpenAPI version pinned to 3.0.3, not 3.1.0.** See prior reasoning — `nullable: true` throughout is invalid OpenAPI 3.1.
- **SDK hooks never destructure `{ data, error, response }` off an awaited `client.METHOD(...)` call, and never narrow directly on `result.error` inside an `if`.** TS 5.9.3 + openapi-fetch 0.12.5 collapses inference to `never` otherwise — verified in isolation. See `packages/sdk/src/hooks/useAuth.ts`.
- **`RegisterInput` uses `businessName`, not `username`/`displayName`.**
- **Business/User split instead of User/Profile split.**
- **Source is a discriminant (`sourceType`) + typed nullable FKs** — now three: `sourceMessageId`, `sourceDeploymentId`, `sourceAdUnitId`. Same reasoning as before, extended.
- **`apps/ad-server` does not use `fastify-openapi-glue` / the shared OpenAPI spec.** Its four routes are public, high-volume, and consumed by embed snippets and tracking pixels, not the LOOPIE web app's typed SDK — a second contract-first pipeline for four routes would be machinery without a benefiting consumer. See `apps/ad-server/README.md`.
- **`AttributionEvent.deploymentId`/`adUnitId`/`campaignId`/`creativeId`/`platform` are all nullable now** (were required). Either `deploymentId` xor `adUnitId` is set, enforced in application code (both `AttributionService.trackClick` and `AdServeService.recordClick`), not a DB constraint — Prisma/MySQL has no clean way to express "exactly one of two nullable FKs" declaratively.
- **`LandingPage.slug` is globally unique**, not per-business — supports clean `/p/{slug}` hosted URLs without a business-id prefix, and sets up custom-domain mapping later. Enforced at the service layer (409 on conflict) and via `@unique` in schema.
- **`Form` structure IS frozen into `PublishedPageVersion` (reversed 2026-08-27 — see "Landing-Page Capture Immutability" below).** Originally only `content`/`theme`/`formId` (a pointer) were snapshotted on publish, so editing a Form's fields after publishing silently changed what an already-live page rendered and validated against. `PublishedPageVersion.formSnapshot` now freezes the field list too. `Form` itself is still a reusable, live entity by design (see the brief: "first-class reusable entities rather than embedded JSON") — editing it freely affects drafts and future publishes, just not already-published versions until they're republished. Soft-deleting a Form is the one thing that still takes effect immediately everywhere, published pages included (a deliberate, separate live gate — see `isFormLive` in "Landing-Page Capture Immutability").
- **Landing-page performance's `leads`/`sales` are computed by joining through `FormSubmission.leadId`**, not a direct `landingPageId` FK on `Lead`/`Sale`. Keeps the Source pattern exactly as it was (no new FK sprawl on the core spine) at the cost of an extra join — acceptable at V1 scale.
- **AdUnit has no `spend` field.** First-party inventory has no external-platform cost; `byPlatform`/`bySource` rows for `LOOPIE`/`AD_UNIT` always report `spend: null`/`0`.
- **`packages/db/tsconfig.json`** now includes `prisma` (previously only `src`), and `bcryptjs`/`@types/bcryptjs` moved to `packages/db`'s own dependencies (were only in `apps/server`'s) — `prisma/seed.ts` uses bcrypt directly and was silently unchecked before this pass.
- **`apps/server/vitest.config.ts` sets `fileParallelism: false`.** Found live: Vitest's default parallel-file execution against one shared real database, combined with `setup.ts`'s global `afterEach` table wipe, caused test files to delete each other's mid-test data — surfaced as spurious 401s that had nothing to do with auth. Serial file execution fixed it; the underlying cause (one shared DB, no per-file isolation) is worth revisiting if the suite grows large enough for serial execution to matter.
- **Click redirects append `?sid=<sessionId>`** to any absolute destination URL — a `withSid()` helper in `apps/server/src/services/AttributionService.ts`, duplicated (not shared, different packages) in `apps/ad-server/src/services/AdServeService.ts`. Found live, not by inspection — see "Live Database: Verified" above.
- **`apps/web` was scaffolded by hand, not `pnpm create vite`.** `pnpm dlx` failed with a persistent `ENOENT` on the pnpm dlx cache in this environment (survived a cache clear). Every file `create-vite` would have generated was instead copied from the skill's own templates (`templates/web/*`, `templates/configs/*`) — the templates-first path the skill already prefers, so no functional gap versus the scripted path.
- **`Shell.tsx`'s Home nav item points at `/home`, not `/`,** and `App.tsx`'s index/catch-all routes redirect to `/home`, not the alphabetically-first generated route (`/contacts`). `scripts/generate-pages.ts` has no way to know which page is meant to be the app's landing screen — it defaults to the first route it encounters — so this needed a manual fix to match `docs/00-unified-ia-navigation.md`'s actual IA (Home is the landing screen). Caught by the Playwright login test failing on `/contacts` instead of `/home`.
- **Landing Pages/Forms/Ad Units are not in the top-level Shell nav** — `docs/architecture/00-unified-ia-navigation.md` places them under Campaign detail (Forms still have no dedicated surface). `Shell.tsx` stays Home · Campaigns · Messages. **Resolved 2026-08-26**: Campaign detail sub-nav is Overview → Budget → Creatives → Ad Units → Leads. Landing Pages remain reachable from Overview destination + `/landing-pages`.
- **IA revised 2026-08-27: nav dropped from 5 top-level items to 3 (`Home · Campaigns · Messages`), reversing the earlier `Advertising` label back to `Campaigns` and demoting Contacts and Results/Reports out of the top nav entirely.** Contacts now lives under `Messages → Contacts`; there is no blended "Results"/"Reports" page — each surface gets its own `Performance` section instead (`Campaigns → Performance`, `Messages → Performance`), with Home staying the one operational landing screen. Explicit user preference, not a technical constraint — full rationale in `docs/00-unified-ia-navigation.md`'s "Revision (2026-08-27)" section. `Shell.tsx` was updated to match; the 76 already-generated routes (`/contacts`, `/campaigns`, etc. from `pages:generate`) did not change — only which ones the Shell links to directly.
- **A generated create-form page's post-success `navigate(-1)` is fragile — found live, not by inspection, while building the Landing Page slice.** It depends on the SPA's in-memory history stack; reach the page by a direct URL (typed, bookmarked, or a Playwright `page.goto()`) rather than clicking a `<Link>`, and "back" falls through to a real browser navigation that reloads the wrong page instead of an SPA one. Fixed in `genCreateFormPage`: a top-level create (no parent path param) whose response is a single resource with an `id` now navigates straight to `${path}/${result.data.id}` — its own new detail page — instead of `navigate(-1)`. A nested create (e.g. a deployment under a campaign) or a non-resource bulk response (`ImportContactsInput` → `{created, skipped}`, no `id`) still uses `navigate(-1)`, since neither has a standalone detail page to land on.
- **`useCampaigns.ts`'s hand-written `CreateCampaignInput.platforms` type had drifted from the OpenAPI spec** — it excluded `'LOOPIE'`, even though `openapi.yaml` has allowed it since the ad-serving extension (selecting `LOOPIE` as a campaign platform creates first-party `AdUnit` rows instead of a `Deployment` — see the spec's own description on that field). - **`packages/db/src/signedSid.ts`'s `issueSid` had no explicit parameter type** (`sessionId = randomUUID()`) — TS infers the parameter's type from the default value, and `randomUUID()`'s return type is a UUID template-literal type, not plain `string`, so passing any other `string` (e.g. from `verifySid()`) failed to typecheck. Pre-existing, unrelated to this session's other work; surfaced only because this was the first time `pnpm typecheck` was run across every package rather than just `apps/web`. Fixed with an explicit `sessionId: string` annotation.
- **Money & Ledger (2026-08-26): no stored balances.** `FinancialAccount` has no balance field; `LedgerTransaction`/`LedgerEntry` have no `updatedAt` and are never edited after post. `Campaign.budget` stays a Decimal planning field; available funds come from `CLIENT_AD_FUNDS` ledger balance, reserved funds from `CLIENT_FUNDS_RESERVED` entries scoped by `campaignId`, and platform-reported vs settled spend live as separate columns on `AdSpend` (reconciliation persists a comparison row rather than overwriting either). Integer `amountMinor` + ISO currency only. All ledger writes go through `FinanceService` / `lib/finance/ledger.ts#postLedger` inside Prisma `$transaction`. Frontend finance pages were not generated this pass (`pnpm pages:generate` not run) — contract, service, SDK hooks, and integration tests only.
