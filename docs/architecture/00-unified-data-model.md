# Unified Data Model

## Purpose
Messaging (`04-customer-lead-model.md`, `05-audience-segmentation-spec.md`, `08-content-template-system.md`) and Campaigns (`02-campaign-model-spec.md`, `03-creative-asset-system.md`, `06-crm-lite-requirements.md`) each defined their own Contact/Lead/Sale schema and their own content system. This doc reconciles both into one model so a lead generated by a paid campaign and a lead generated by a text reply are the *same kind of record*, followed up by the *same automation engine*, and reported in the *same funnel*.

This doc is canonical where it overlaps with the two packs. Where a pack's doc conflicts with this one, this one wins.

## Design Principle
**Acquisition is plural, everything downstream is singular.**

A business reaches people two ways — paid media (Campaigns) and owned outreach (Messaging) — but only one Contact record, one Lead pipeline, one Sale ledger, one Interaction timeline, and one Automation engine should exist per business. Campaign and Message are both just *sources* that feed the same spine.

```text
              ┌─────────────┐        ┌─────────────┐
              │  Campaign   │        │   Message   │
              │ (paid, ext. │        │ (owned,     │
              │  platforms) │        │  Email/Text/│
              │             │        │  Social)    │
              └──────┬──────┘        └──────┬──────┘
                     │  Deployment           │
                     ▼                       ▼
              ┌─────────────────────────────────────┐
              │              Source                  │
              │   (polymorphic: message | deployment)│
              └──────────────────┬────────────────────┘
                                  ▼
        Contact → Interaction → Lead → Sale
                                  ▲
                                  │
                          Automation Rules
                     (trigger → wait → condition → action)
```

## Core Entities

### Business
The account/tenant. Owns everything below.

### Contact
One person or organization, regardless of how they entered the system.

Fields: `id, business_id, name, email, phone, company, source, tags[], created_at, last_contacted_at, channel_eligibility {email, sms, social} (consent + opt-out per channel)`

Rule (from Messaging model, now global): **never duplicate a person because of lifecycle or acquisition-channel changes.** A contact created from a Meta lead form and later emailed directly is still one row.

### Audience
A saved or temporary group of Contacts, used both to select message recipients and to segment CRM-lite reporting.

Types: `predefined, saved_filter, manual_list, imported_list`

Filters now span both packs' vocabularies: relationship (lead status, purchase count, LTV), communication (has email/mobile, eligibility, replied), business metadata (company, location, tags), sales (stage, quote sent, won/lost), **and acquisition** (source campaign, source creative, source platform, date acquired). A campaign's leads are just another audience filter, not a separate object.

### Asset
Atomic reusable source material owned by the business, not by a single Message or Campaign: image, text block, video, audio, logo. Replaces the idea of two separate libraries — Messaging's implicit template content and Campaigns' asset library draw from this one store.

### Template
A composition of Assets/text intended for a **Message** send (email/text/social). Fields: `name, channel, purpose, subject, body, media, cta, personalization_tokens, suggested_audience_id, suggested_automation_id`.

### Creative
A composition of Assets intended for a **Campaign** deployment on an ad platform. Fields: `name, asset_ids[], hosted_url, version`. Creative history is immutable — a meaningful change creates a new version, never an overwrite, so performance stays attributable.

Template and Creative stay distinct types (different constraints: platform specs and immutable versioning for Creative vs. mutable, personalization-token-driven content for Template) but both **read from the same Asset library**, so a product photo used in an email can also be used in a Meta ad without re-uploading.

### Message
One organic send. Fields: `id, business_id, channel (email|text|social), subject, audience_id, template_id (nullable), body, status, scheduled_at, sent_at, automation_id (nullable)`.

### Campaign
One paid-media run. Fields: `id, business_id, name, creative_ids[], platforms[], budget, start_date, end_date, destination_url, status`. Lifecycle: `Draft → Active → Paused → Active → Ended`.

### Deployment
Links one Creative to one external ad-platform object under a Campaign. Fields: `id, campaign_id, creative_id, platform, external_campaign_id, external_ad_set_id, external_ad_id, status, spend, impressions, clicks, conversions, last_synced_at`.

### Source (new — the reconciling concept)
A polymorphic pointer used on Lead, Sale, and Interaction so both packs' notion of "where this came from" collapses into one field pair instead of two incompatible schemas.

```text
source_type: message | deployment | manual | import
source_id:   <message_id> | <deployment_id> | null | null
```

Everything Campaigns called `campaignId/creativeId/deploymentId/platform/clickId` and everything Messaging called `source message` is derived by joining through this one pointer (`deployment → creative → campaign`, or `message` directly).

### Lead
A contact with active sales potential. Fields: `id, contact_id, stage, owner, estimated_value, source_type, source_id, click_id (nullable), landing_session_id (nullable), opened_at, closed_at`.

`click_id` / `landing_session_id` are only populated when `source_type = deployment` — they're the attribution identifiers Campaigns needed, kept on the same Lead row rather than a separate CRM-lite lead table.

### Sale
Fields: `id, contact_id, lead_id (nullable), amount, date, product_or_service, source_type, source_id, notes`.

Same Source pointer as Lead — a sale attributed to a campaign and a sale attributed to a message are the same table.

### Interaction
The single event timeline per contact. Fields: `id, contact_id, type, source_type, source_id, timestamp, metadata`.

`type` now spans both packs: `email_sent, text_sent, social_post_sent, reply, call_logged, note, status_change, quote_sent, sale_recorded, ad_click, form_submitted`. This is what renders in the contact side panel (`03-messaging-ux-spec.md`'s "Contact Detail") regardless of whether the touchpoint came from a Message or a Campaign-driven ad click/form.

### AttributionEvent
Pre-identity tracking, kept separate from Interaction because it's anonymous until form submission. Fields: `id, campaign_id, creative_id, deployment_id, platform, timestamp, session_id, click_id`. On form submission, the session resolves to a Contact (existing or new) and a Lead is created with `source_type = deployment`, `source_id = deployment_id` — this is the exact identity-transition moment `05-attribution-funnel-spec.md` describes.

### Automation (rule)
Unchanged shape from `06-automation-rules.md` (`Trigger → Wait → Condition → Action → Stop`), with the trigger set widened so it fires regardless of source:

- Triggers: `message_sent, contact_replies, lead_created (any source_type), lead_status_changed, sale_recorded, date_reached`
- This is the actual fix for the biggest gap between the two packs: Campaigns had no follow-up mechanism. A Lead created from a Meta form now hits the same trigger (`lead_created`) as a Lead created from a text reply, so "wait 1 day → send text" applies to both without new engineering.

### PerformanceSnapshot
Generalized rollup so reporting doesn't need two implementations. Fields: `entity_type (message|campaign|creative|deployment), entity_id, period, sent_or_views, opened_or_clicks, replied, leads, sales, revenue, spend (null for organic)`.

## Lifecycle (canonical — replaces both packs' versions)
Campaigns' CRM-lite doc simplified the pipeline to `Lead → Customer → Sale`, which treats Sale as a stage after Customer instead of the event that *causes* the Won/Customer transition. The fuller Messaging lifecycle is adopted as canonical:

```text
Contact
  ↓
Lead (New)
  ↓
Contacted
  ↓
Qualified
  ↓
Quoted
  ↓
Won ──→ Customer (derived label, not a stored stage)
  ↘
   Lost
```

A Customer can generate a new Lead later (repeat sale) — this applies identically whether the repeat lead came from a follow-up message or a retargeting campaign.

## Reconciliation Notes
- **Contact**: merged as-is; Messaging's version already had everything Campaigns' CRM-lite needed (channel eligibility, tags, source).
- **Lead / Sale**: merged via the new `source_type`/`source_id` pointer instead of maintaining `campaignId/creativeId/deploymentId` fields on one schema and `source message` on the other.
- **Interaction**: extended with `ad_click` and `form_submitted` so campaign-driven touchpoints show up in the same contact timeline Messaging already renders.
- **Templates vs. Creative**: kept separate (different platform/versioning constraints) but unified under one Asset library — this was previously two disconnected content systems.
- **Automation**: no new entity, only a widened trigger (`lead_created` instead of being implicitly message-only) — this is the mechanism that lets a campaign lead get an automatic follow-up text, which no doc currently specifies.
- **Audience**: filter set extended to include campaign/creative/platform source, so "leads from Campaign X" is an Audience, not a separate concept.
- **Lifecycle**: Campaigns' `Lead → Customer → Sale` is dropped in favor of Messaging's fuller stage model; Sale becomes an event, not a stage.

## Resolved: Campaign and Message Stay Distinct Domain Concepts
Campaign is not renamed, generalized, or merged with Message into a shared object like "Outreach" or "Activity." They remain two acquisition mechanisms with genuinely different workflows — Campaign deals with creatives, platforms, budget, and deployment; Message deals with recipients, scheduling, templates, and personalization. Collapsing them into one generic entity would lose that distinction for no benefit, since:

- **Campaign** = a paid-media run (`source_type = deployment`).
- **Message** = an owned/organic send (`source_type = message`).
- Both are `source_type` values feeding one `Contact → Lead → Sale → Interaction` model — the shared spine, not a shared front-end object.
- `Source` is a backend/data-joining abstraction only. It is never a user-facing object, table, or label — it exists so Lead, Sale, and Interaction can point at either origin through one field pair instead of two schemas.
- Automation triggers (`lead_created` above all) must stay source-agnostic — a trigger cannot silently mean "message reply only," or leads originating from a Campaign deployment never receive automatic follow-up, reopening the exact gap this doc was written to close.
- Asset remains shared by both Template (Message-oriented) and Creative (Campaign-oriented) — one library, two composition types.

UI naming, top-level navigation, and how much of "Campaign" vocabulary surfaces to users is an information-architecture decision, not a data-model one, and is out of scope for this doc. See the UX/IA spec for that resolution.

## Extension (2026-08-26): Landing Pages, Forms, First-Party Ads
The original chain above stopped at Deployment/Message → Contact. It's now: `Campaign → Creative → Deployment (external) or AdUnit (first-party) → LandingPage → Form → FormSubmission → Contact → Lead → Message/Automation → Sale`. Three additions, none of which touch the shared spine's shape:

**LandingPageTemplate → LandingPage → PublishedPageVersion.** Same "acquisition is plural, downstream is singular" logic applied to page authoring: `LandingPageTemplate` defines a structured, versioned manifest of editable sections (not markup — deliberately not a freeform builder); `LandingPage` is the draft working copy; `PublishedPageVersion` is an immutable snapshot taken on publish. `LandingPageTemplate.businessId` is nullable and `formatVersion` is tracked independently of LOOPIE's own release specifically so an external template catalog can supply templates LOOPIE imports later, without a schema change.

**Form → FormField → FormSubmission**, first-class and reusable — not JSON embedded in a page, so the same Form can be attached to multiple LandingPages. `FormSubmission` is the raw capture record; submitting one is the identity transition (anonymous session → FormSubmission → resolve/create Contact → create Lead) and always resolves through the same function the original attribution flow already used (`resolveContactAndLead` in the reference implementation) — landing pages did not get a second Contact/Lead model.

**AdUnit** is first-party creative LOOPIE serves itself, deliberately kept a separate model from Deployment rather than overloading it — Deployment represents creative running on an external ad platform we don't control serving for; AdUnit is creative we do. Both are just more `source_type` values (`DEPLOYMENT`, now joined by `AD_UNIT`) feeding the identical Lead/Sale/Interaction spine, exactly like Campaign and Message did before them. First-party serving (impressions, click redirects, embeds) runs as its own deployable service, separate from the account-management API, because it's a public, latency-sensitive traffic path with different scaling and failure characteristics — not because the data model needed it separated.

**What stayed a backend-only abstraction, unchanged in kind:** `Source` is still never a user-facing object — Lead/Sale/Interaction now carry a third nullable typed pointer (`sourceAdUnitId`, alongside `sourceMessageId`/`sourceDeploymentId`) rather than becoming truly polymorphic. Attribution metrics (impressions, clicks, page views, form submissions, conversion rate) roll up through Landing Page → Creative → Campaign → Platform the same way Creative × Platform performance already did — this was additive to the reporting layer, not a redesign of it.
