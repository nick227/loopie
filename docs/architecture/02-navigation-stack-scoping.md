# Navigation Stack Scoping (2026-08-29)

## Purpose and Status

Scoped in response to `docs/strategy/03-product-principles.md`'s "Navigation Model — Single Focus, Adaptive Context" section, which explicitly deferred the architecture question to this doc rather than deciding it inline. Same discipline as `01-external-ad-monitoring-contract.md`: this is findings grounded in the actual current routing/Shell code, plus open questions to decide — not a build, and not a redesign proposal dressed up as findings.

**Headline, stated up front**: unlike the ad-monitoring contract (which turned out to already exist), this one _is_ a real gap. There is no navigation-stack behavior today beyond what React Router's URL history gives for free. Building "single focus, adaptive context" is genuine new architecture, not a UI-sequencing change on top of something already correct.

## What Exists Today

- **One persistent `Shell`, wrapping every route uniformly.** `App.tsx`'s route tree has exactly one `<Route element={<Shell />}>` parent; every page (Inbox, a Contact, a Campaign, a Page editor) renders as its `<Outlet />` child. There is currently no concept of "this route is deep, hide the chrome" — the sidebar/bottom-nav render unconditionally on every single page. Nothing about "global navigation goes quiet once deep" exists structurally; it would need `Shell` (or a route-level convention it reads) to know how deep the current route is.
- **Sub-entity sections are already real routes, not client-side tabs — which is a genuine head start.** Confirmed by reading `App.tsx`: the legacy Campaign detail's Budget/Creatives/Ad Units/Leads (`/campaigns/:campaignId/budget`, `/campaigns/:campaignId/leads`, etc.) are distinct top-level routes, each its own page component. This means browser Back already "works" for them today in the crude sense of returning to the previous URL — but only in that crude sense; nothing preserves what the previous page's scroll position, search text, or filter selections were, because the component fully unmounts on navigate and remounts fresh when Back returns to it. **State continuity is not a small gap to backfill — it doesn't exist today for any multi-step flow in this app.**
- **The canonical `Advertisements` (`/ads/:adId`) and `Contacts` (`/contacts/:contactId`) detail pages are single, unsegmented pages today** — `AdPage.tsx` is one scrolling page (destinations/metrics/manage-modal, all in one), `ContactPage.tsx` is one scrolling page (identity/linked-systems/timeline). Neither has the `Overview | Activity | Messages | Sales`-style entity-local tab structure the principles doc describes as the target shape — that's aspirational, not something to assume is half-built.
- **Desktop split-pane precedent exists exactly once**, and it's legacy: the CRM mockup era (referenced in `docs/design/00-design-language-spec.md`'s "Desktop: Split Panes & the Pipeline Stepper" section) described a list+detail split pane for Contacts, never built. There's no shipped `SplitDetailLayout` or equivalent to build the desktop companion-pane behavior on top of — it would be new.

## What "Single Focus, Adaptive Context" Actually Requires, Technically

Broken into the three separable technical problems the principle bundles together — worth keeping separate because they have different costs and don't have to land together:

1. **Conditional chrome ("global nav goes quiet once deep").** Needs a "how deep is the current route" signal `Shell` can read — plausibly a route convention (e.g., routes nested under a nesting level, or a small context a deep page sets on mount) rather than a hardcoded path list, since it has to work for every future entity-detail page, not just the ones that exist today. The mechanically simplest version: a route-level flag/layout choice ("this page renders with full chrome" vs. "this page renders chrome-light, showing only a back affordance") — closer to a per-route layout decision than a global depth counter.
2. **State continuity (scroll, filters, search text, selected segment) across navigate/Back.** The real one. React Router's default unmount/remount-on-navigate behavior loses all of this today. Real options, not chosen here: (a) keep list-page state in a store keyed by route so it survives unmount (a small amount of new state-management surface, not a rewrite), (b) restructure so "list" and "its entity" are siblings under one persistting parent route rather than two independently-mounted pages (bigger restructure, closer to true master-detail), (c) rely on the browser's native scroll restoration plus URL search-params for filters/search (cheapest, but doesn't cover "selected Inbox segment" or arbitrary local UI state on its own). These aren't mutually exclusive — likely some combination, but which combination is a real decision, not made here.
3. **Desktop companion pane.** Needs a shared layout primitive: "primary entity + optional secondary pane, where the pane's content is chosen contextually (leads for a campaign, submissions for a page, activity for a contact) and can itself be replaced by a deeper focused view when something inside the pane is tapped." This is new, purpose-built UI, not a retrofit of the abandoned CRM split-pane mockup — that one was never load-bearing code.

None of these three block each other — (1) could land as a visual pass without solving (2); (2) is the one with the most user-facing cost if skipped (navigation feels punishing if Back loses your place); (3) is desktop-only and could reasonably follow (1)+(2) once those are proven on mobile-shaped screens first, which is also the platform the principles doc treats as the baseline case.

## A Real, Separate Gap Found Along the Way

Not a navigation-architecture question, but directly relevant to the principles doc's stated MVP-loop requirement ("see result in Inbox when that ad and that form are interacted with separately"): traced the actual notification path (`apps/server/src/lib/submissionInbox.ts`'s `notifyFormSubmission`, `apps/server/src/lib/adRunInbox.ts`'s `notifyAdRunEvent`).

- **The attribution data is real and already there** — a Lead created from an ad-driven form submission already carries `sourceAdRunId` (which specific ad) alongside the form/page context, confirmed in `01-external-ad-monitoring-contract.md`'s Question 5.
- **A raw ad click, by itself, correctly produces zero Inbox activity** — `adRunInbox.ts`'s own comment states the deliberate scope: "routine successful syncs, every provider poll, and small spend fluctuations are audit-only" — a click is exactly this category of routine, high-volume signal, and per-click Inbox rows would be noise, not a gap.
- **The actual gap**: `notifyFormSubmission`'s Inbox copy — `"Submitted {formName}"` (the Contact thread) and `"New submission from {contact.name}"` (the Page thread) — **never names which ad drove the click**, even when `sourceAdRunId` is set. The data exists on the Lead; the Inbox notification a user actually reads doesn't surface it. A user would have to click through to the Lead/Contact detail to see the ad attribution. Whether this is worth fixing (and how — the two-projection pattern `notifyFormSubmission` already uses could plausibly grow a third context, or enrich the existing two, once the caller knows the session's attribution) is a real, separate, small scoping question — not decided here, not part of the navigation-stack work, flagged so it doesn't get lost.

## Open Questions — Not Decided Here

- Which of the three technical pieces (conditional chrome, state continuity, desktop companion pane) to build first, and whether all three are needed before any of this ships, or whether conditional chrome + state continuity alone (mobile-shaped, single-stack) is a legitimate first milestone with desktop's companion pane following later.
- The state-continuity mechanism (the three options sketched above, or a combination) — a real engineering decision with real tradeoffs, not obvious from principle alone. **Now has a concrete rule to build against**: `03-product-principles.md`'s "Singleton, Collection, Entity" grammar (2026-08-29) — Back from an entity must unwind to whichever of {its collection, Inbox} actually opened it, not a fixed parent, so whatever mechanism gets chosen has to carry "how did I get here," not just "what was scrolled/filtered where."

- Whether legacy Campaign detail's already-real sub-routes are a useful pattern to generalize from, or specifically legacy scaffolding not worth building the new model around (per the existing "legacy, orphaned-from-nav" status documented in `00-unified-ia-navigation.md`).
- **New (2026-08-29): a business-identity singleton is now part of the target model** (`03-product-principles.md`'s First-Login Experience step 0 and Inbox identity card) and it's a `Singleton` in the grammar above — but `Business` has no identity fields (`location`/`industry`/`targetAudience`/`socialProfiles`/`logo`) yet, and the existing `/profile` route is a user-account page, not this singleton.
