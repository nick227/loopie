# Ads defaults and catalog proposal

2026-09-10 · Code audit and proposal only; no implementation changes.

## 1. Five useful starter Ads

Create five editable business-owned drafts. Populate only known business facts; missing offers, products, and dates remain explicit completion fields. Do not invent discounts, testimonials, prices, or events. A name-only business can still receive a finished typographic introduction and contact creative; the remaining drafts become useful guided starting points.

Sizes below are proposed internal output presets, not verified platform specifications or promises of connector support: square **1080×1080 (1:1)**, portrait **1080×1350 (4:5)**, story **1080×1920 (9:16)**, landscape **1200×628 (~1.91:1)**, compact display **300×250 (6:5)**. Placement rules must be checked when enabling delivery.

## 3. Smallest model: Ad Type → Creative Layout → Style → Rendition

Prove the composition and capture first, then build **code registries** for the five starters. The chain describes selection and rendering, not ownership or a requirement for four database tables.

- **Ad Type:** stable Ads-owned key, label, purpose, default objective, and small typed content schema. Types describe intent (introduction, contact, spotlight, offer, event), not visual arrangement. Objective is separately selected on the creative (`AWARENESS` or `TRAFFIC`); a type suggests rather than fixes it.
- **Creative Layout:** stable key/version, renderer, defaults, field limits, and explicitly implemented output presets. Layouts are reusable across Ad Types from the start: image-left/text-right can serve Contact, Spotlight, Offer, and Event. Each type lists suggested layout keys and a small binding function that maps its content to the renderer inputs (for example, event date or offer value into a supporting text block). Multiple types can use one layout, and each type can offer multiple layouts. Validate required inputs and test the registered combinations; no compatibility engine or shared capability graph. Select at creation; create a new Ad to change layout initially. Register today's renderer as the preserved generic photo-overlay layout, including all existing format presets and the untouched legacy fallback.
- **Style:** Ads-specific preset key/version and resolved palette/font/treatment tokens. Style changes cannot rearrange content. A photo poster and a split composition are layouts; bold, warm, or minimal are style classifications. Permit only presets implemented by that layout through a simple list, not a capability graph.
- **Rendition preset:** initially just a key, pixel dimensions, and image format for square and portrait. Add placement safe areas, quality settings, and copy/crop overrides when an actual output needs them. Placement/platform is a separate many-to-many recommendation mapping: one square output can serve several destinations. A layout must explicitly compose each supported ratio; shrinking a story into a banner is insufficient.

For the registry milestone, keep type-specific content and layout bindings in code-backed fixtures first. Five Ad Types do not require five unique compositions: deliberately exercise a shared layout across at least Contact and Spotlight. Distinguish text painted inside the image from companion `primaryText`. Keep existing common copy/CTA/destination and Asset fields authoritative.

When saving starter Ads becomes necessary, add only the draft fields needed to retain the selected type/layout/style, type-specific content, and starter identity. Preserve current Advertisement behavior and old snapshots. New content needs a snapshot extension when it enters publishing, not before the creative proof.

**Deferred until export/publishing needs persistence:** an AdRendition record linking a published version and output preset to a generated file and its dimensions/MIME. Start with the fields that workflow needs. Queue status, retries, leases, render hashes, durable-storage guarantees, and retention policy are production design decisions to make at that point, not prerequisites for compositions or registry previews. A synchronous capture returning image bytes or a local proof artifact is sufficient initially.

When generated files enter delivery, render from the pinned published snapshot and pin the selected output in the delivery payload. Brand or registry updates must not silently change published creatives. No AdRun change is needed for the creative proof or starter registries. Awareness means destination-optional content, not bypassing a placement that requires a link. Keep link/click metadata outside the bitmap and retain accessible text in HTML wrappers.

## 4. Reusing screenshots: proof now, production later

[PageThumbnailService](../../apps/server/src/services/PageThumbnailService.ts), [pageThumbnailCapture](../../apps/server/src/lib/pageThumbnailCapture.ts), [storage](../../apps/server/src/lib/mediaStorage/index.ts), and [worker](../../apps/server/src/worker.ts) provide the foundation: batched Chromium sessions, queued work, checksum checks before commit, failure recording/repair, and local/R2 persistence.

For the first square/portrait proof, use reviewed HTML/CSS and known assets through the existing capture infrastructure. Only sizing and reliable visual capture are immediate requirements:

- Capture is fixed to a 1280×800 viewport at 0.5 scale, producing 640×400 JPEG at quality 72. Parameterize a neutral capture primitive; retain the exact Page wrapper defaults. Add an Ads document wrapper with explicit canvas sizing. Existing rem-based text caps and stylesheet ordering require visual checks at export resolution.
- Capture waits for DOM readiness plus 400 ms, not successful image decode/font readiness. Ads need bounded font/image readiness, deterministic assets, animation freezing, and clipping/overflow checks. PNG or high-quality JPEG should be selectable.
  The following audit findings matter later; they do not gate the reviewed local composition proof:

- Isolation has no inherited credentials, but JavaScript is enabled. The URL guard blocks some literal private addresses; it is **not a strict host allowlist** and does not resolve DNS/private IPv6 comprehensively. Before accepting untrusted runtime HTML, use isolated, script-disabled capture and controlled asset/font origins with network-level private-address protection. AI can first author structured content and reviewed HTML/CSS layouts; arbitrary runtime scripts are unnecessary.
- `saveThumbnailFile` fixes JPEG naming/MIME, has a 4 MB cap, and tolerates R2 write failure with a local copy. When persistent exports ship, reuse storage backends through an Ads output writer with explicit MIME, size policy, and confirmed durable availability. The proof can return bytes or save local files.
- Reuse queue/checksum patterns, not PageThumbnail rows or lifecycle. Page jobs discard superseded published versions; an old Ad version can still be pinned by a live deployment and must retain its renditions. If a background rendition queue becomes necessary, then evaluate atomic claims, retries, and lease recovery against its actual concurrency needs.

## 5. Taxonomy and shared boundary

Keep Ads purpose types, layout IDs, style classifications/presets, objectives, placement mappings, and rendition presets Ads-owned. Optional industry/genre tags rank starter suggestions; they do not determine rendering compatibility. Start as controlled lists in the registry. Do not import PageType, Capability, Page layout slot contracts, PageCompatibilityService, or Page genre/style values.

Justified sharing is already concrete: Asset/media storage, business identity/logo, Page destination references, and the extracted capture primitive. Seed Ads tokens from business branding where available, then snapshot them; do not require PAGE_THEME_PRESETS or introduce cross-domain brand synchronization. Stable keys, versioning, and catalog filter patterns can follow Pages' mechanism without sharing taxonomy rows or creating a universal catalog service.

The existing strategy drafts remain untouched. This proposal specifically replaces their assumptions that each Ad Type needs exactly one layout, that Page style tokens must become a shared dependency, and that the current capture guard is an allowlist.

## 6. Small phased roadmap

1. **Build one HTML/CSS composition.** Create a useful business introduction creative within the existing ad-renderer approach. Review its typography, imagery, copy, and hierarchy. Preserve existing renderer paths. No new tables or job machinery.
2. **Render square + portrait reliably.** Use the existing screenshot infrastructure with an Ads sizing wrapper and bounded font/image readiness. Inspect real image outputs for dimensions, legibility, cropping, and overflow; verify unchanged Page thumbnail behavior. Return bytes or local artifacts. No rendition persistence, new snapshot hashes, leases, or storage redesign.
3. **Build the five starter Ad Types in code registries.** Define typed content, reusable layout bindings, styles, and sample business data. Preview each starter at both proven sizes; exercise at least one layout across multiple types. Show missing business facts explicitly. This milestone proves creative variety and reuse without persistent rendition jobs. When wiring business-owned drafts, add minimal draft fields and an idempotent `provisionDefaultAds(tx, business)` beside onboarding; preserve deleted starter identities, never overwrite edited Ads, and never create spend/runs automatically. Keep Pages provisioning internals untouched.
4. **Persist only for a concrete export/publishing workflow.** Extend snapshots for the new creative input when publishing is enabled. Add AdRendition records if outputs need durable retrieval/version pinning; add background jobs only if synchronous generation no longer meets that workflow. Decide hashes, retries, storage guarantees, safe areas, and retention from those requirements. Test the persistence and delivery behavior actually introduced, including tenant isolation and published-output immutability.

After these milestones, grow layouts, styles, placements, and catalog filters from demand. A future positioned text/media composition can become another renderer behind the same HTML→image interface; defer its editor, layer model, platform automation, and layout switching.

Implementation should be isolated to Ads plus a backwards-compatible capture/storage utility extraction. Do not modify the current Pages migration, compatibility work, or its uncommitted files.
